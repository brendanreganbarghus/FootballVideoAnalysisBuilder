Innovation Day developer setup

From a clean clone to an isolated local experiment.

Code comes from Git. Restricted video and approved models come from the controlled artifact store. Fresh detections, tracks, and provisional events run locally. Runs needed by the team are published into an append-only, checksummed shared catalog; governed review decisions and passed baselines remain available to every authorized developer.

Alfheim is internal non-commercial research material. Do not copy it into Git, a pull request, chat, public storage or an anonymous sharing link. Confirm access rights before sharing the OneDrive folder.
Source control

Clone and isolate your work

Start from the current validated integration branch. Use one feature branch per workstream.

git clone git@github.com:brendanreganbarghus/FootballVideoAnalysisBuilder.git
cd FootballVideoAnalysisBuilder
git switch main
git pull --ff-only
git switch -c feature/<short-workstream-name>

Start new work from the current validated main branch and keep one independently reviewable feature per branch.

Open Camera Calibration & Overlays to show, redraw, undo, finish, restore, or download the actual camera-mapped pitch boundary and goal frames. Innovation reads the Alfheim calibration while keeping its engine, outputs, decisions, and publication gates isolated from the Live workflow.

The controlled Innovation workflow lists Alfheim segments only. The app loads the Alfheim calibration and never displays another dataset as a visual fallback. Add a custom camera with its own raw 30- or 60-second sample; AI controls remain disabled until its calibration is complete.

The governed source chain is Club → Venue → Camera → Recording → Prepared Segment → AI Run. A camera uses a generated UUID plus club, venue, position, and optional manufacturer serial. Select one of its shared raw recordings, choose a start position, and prepare exactly 30 or 60 seconds. AI never receives the full recording.

Fresh outputs stay under benchmarks\alfheim\generated\ or benchmarks\custom-cameras\. Both are ignored by Git. Custom source video and calibration live in 10-master-data\custom-cameras\. Authorized original recordings remain in 10-master-data\; reusable prepared clips and provenance manifests belong in the append-only 15-prepared-segments\ catalog so other developers can select the identical evidence window.

Active dropdown segments are published under 15-prepared-segments\<camera>\<recording>\<segment> with one canonical playable video, immutable metadata, selected workflow artifacts, and checksums. PostgreSQL supplies the shared review history. A fresh checkout therefore discovers the same segment and decisions without copying another developer's local generated directory.

Copilot Canvas workflow

Use Copilot as an independent reviewer, not an engine echo

The app-native Copilot panel keeps the conversation beside the selected video evidence and current review context.

  1. Prepare context: select an existing 30–60 second Innovation segment and build frozen BAC plus cached player context.
  2. Record M# first: review the video independently, record the ordered manual events, and freeze the golden M# ledger before comparing engine output.
  3. Compare M# and E#: automatic links require the same team and canonical event type within one second; display ordinals never define a match.
  4. Use C# only when useful: Copilot proposals are optional diagnostics and cannot control M#, mappings, approval, or publication.
  5. Resolve discrepancies: verify unmatched E# independently; an accepted missing or incorrect M# result authorizes only a general engine fix and cached events-only rebuild.
  6. Protect prior work: rerun the focused and protected regressions and require every published Innovation output hash to remain exact.
  7. Publish: the final gate requires finalized decisions, current source/output hashes, exact M#/E# counts and matches, and a fresh passing regression receipt.

The general Canvas conversation supports the entire prepared clip or the current time ±2 seconds. Event conversations stay attached to the selected M# or E# so evidence, corrections, and authorization remain traceable.

Team workflow

Own separate event families and segments

Shot outcomes Shot attempts, on-target, off-target, saved or blocked evidence.
Goals Goal confirmation and the kick-off restart state.
Set pieces Corners, goal kicks, and goal-line boundary evidence.
Four zones Calibrated zone membership and zone aggregates.
  • Use one branch, worktree, and pull request per event family.
  • Use assigned development segments for tuning and debugging.
  • A shot outcome and a goal are separate facts linked by a stable attempt ID. A goal implies on-target; on-target does not imply a goal.
  • Keep Copilot C# proposals independent from rules-engine E# events until comparison.
  • Rejecting a C# proposal never confirms a nearby E# event.
  • Do not inspect locked blind references before the frozen AI run.
  • Manual review labels are evaluation-only and never become inference inputs or timestamp exceptions.
  • Commit code, tests, small configuration examples and documentation only.
  • Never commit video, model weights, caches, generated tracking media or logs.
Shared runs

Publish inspectable runs without committing large files

python .\scripts\publish-segment-run.py `
  .\benchmarks\custom-cameras\custom-home-main `
  --dataset custom-home-main `
  --status provisional

This writes an immutable run ID, metadata, selected outputs, engine and model fingerprints, performance receipt, and checksums under 40-team-runs\. Add --include-cache only when another developer needs the exact detections and tracks for debugging. "Checked in" means published to this governed catalog, not committed to Git.

Serial merge gate

Rebase, check overlap, and protect every accepted rule

python -m pytest -q
git status --short
git diff --check

Before merge, update from the latest integration branch and check whether an accepted rule already covers the same evidence. Run the focused tests and every protected passed-segment regression. A feature cannot merge when it duplicates a rule, changes unrelated protected events, breaks a regression, or has a stale receipt. After one family merges, the next branch updates to that commit and repeats the complete gate.

Later workflow

Full-match upload and team locking are not implemented yet

The planned extension will upload a rights-cleared full match, produce controlled 30–60 second segments, publish them to the shared catalog, and show whether another developer currently owns a segment. Until that lease exists, camera IDs, shared runs, and passed baseline folders are append-only and must not be overwritten.
